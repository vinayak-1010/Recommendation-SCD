# Requirements Document — Explore Doon Recommendation Engine Upgrade

## Introduction

`scd-explore-doon.html` currently filters, scores, and assembles a day/evening itinerary through `run()`/`eve()` and their helpers (`D`/`E` catalogs, `sc` scoring expression inside `run()`'s `for(const d of D)` loop, `ord()`, `sim()`, `pk()`, `tm()`/`fm()`, `barH()`, `pill()`, `stp()`, `art()`, the `tuned` flag). That pipeline already works correctly for its original, narrower goal (feasibility, return-deadline math, catalog hygiene — see the existing `.kiro/specs/scd-explore-doon/` spec set, now the "baseline" spec). It was **not** designed to produce a geographically coherent, non-repetitive, human-guide-quality itinerary across arbitrary combinations of time window, interests, transport mode, and traffic conditions. This document is the requirements for that upgrade. It supersedes nothing in the baseline spec (requirements.md/design.md/tasks.md 1–7 remain valid and must keep passing); it adds the Stage A/B/C hierarchical-engine, diversity, geographic, traffic, meal, and explainability requirements the product brief calls for, scoped to the existing architecture and hard constraints below.

All acceptance criteria are numbered and EARS-style where natural. Every criterion is traceable to the authoritative product brief (quoted/paraphrased with full detail preserved, not thinned) and anchored to the actual function/data names found in `scd-explore-doon.html`.

## Root problems confirmed by reading the code (ground truth for this upgrade)

1. **Stage C ("build a coherent trip") does not exist.** In `run()`, after at most one Mountain_Trip/Full_Day_Trip (`mt`) is chosen, the loop `for(const x of C){if(x.mt||x.full||x.u||x.onroute||S.includes(x))continue;S.push(x);if(S.length>=4)break}` just walks the globally sorted-by-score candidate list `C` (sorted once by `sc` descending) and appends the next-highest scorers until 4 stops, with zero awareness of which stops are near each other. This is exactly the "independently pick the highest-scoring destination and append" anti-pattern the brief says to avoid.
2. **There is no geographic/cluster field or route-adjacency model anywhere in `D` or `E`.** The only location-adjacent fields are `rt` (a key into the `R` direction-text table, not a location), `mt`/`far`/`onroute`/`full` (trip-shape flags), and `tv` (a single one-way travel minutes from campus, not minutes between arbitrary stop pairs). Inter-stop travel time in `sim()`'s `leg()` helper is a flat heuristic (`a.mt?Math.round(a.tv*.9):(a.onroute?Math.round(b.tv*.5+10):25)`) — notably a **flat 25-minute city-to-city leg regardless of which two city-area stops are involved** (this flat estimate is baseline Open Question #5, already known and unresolved). There is no way today to tell whether two chosen stops are in the same area or on opposite sides of town.
3. **No diversity/category-repetition control exists.** Scoring (`sc`) rewards vibe-match ratio (`it = m.length/sel.length`) and four other weighted terms, but nothing in `sc` or in the `S`-building loop checks whether a candidate's category/experience type duplicates one already selected. Selecting multiple vibes (e.g. nature + views + adventure, which many `D` entries tag simultaneously — `land`, `geo`, `bha`, `rob` all carry 3–4 overlapping tags) can and does inflate scores for near-duplicate experiences with no corrective term.
4. **"Alternatives" do not exist as a concept.** The `row()` suggestion rail ("More ideas"/"Best matches"/"Famous cafés & restaurants") is cosmetic — it is not scoped per-stop, does not explain why it's an alternative to a specific stop, is not excluded from being also offered as a "replacement," and selecting a rail card does nothing (no click handler recomputes the itinerary).
5. **Transport mode's effect on recommendations is binary/filter-only, not estimation-aware.** `tr==='bike'` only ever hard-excludes `mt`/`far` entries for non-`fr` groups and nudges `trn` by a fixed `.2` in the score; it never changes travel-time estimates, never reflects parking/congestion differences for `car`, and there is no Sunday-specific traffic-timing model beyond the single `risk=(d.mt?(st>=540?.6:.3):.1)` term and the static `tod` time-of-day term, both scoped only to Mountain_Trip entries.
6. **Meal planning is a single generic "add one food/cafe, sc:.4" step** (`if(use>=300&&(!mt||!mt.full)){const L=pickE(['food','cafe'],sel,gr,1)[0];...}`), with no breakfast/lunch/quick-cafe differentiation, no "near the other chosen stop" preference, and the lowest score of any stop in the plan — meaning it is first to be dropped by the trimming loop (`while(...){const drop=[...I].filter(x=>!x.mt&&!x.full).sort((a,b)=>a.sc-b.sc)[0];...}`), confirmed as baseline Open Question #6.
7. **Per-stop rationale and inter-stop "why this transition" text do not exist.** `stop()` renders name/photo/note/badges/"your vibe" tag match/duration/directions, but nothing says why this stop over another, or why the next stop logically follows.

These seven points are the "underlying problems" the brief asks to fix; they define the scope of every functional requirement below.

## Hard constraints (apply to every downstream design/plan/code step; restated here as binding, not optional)

- **HC-1 Single file, no build step.** `scd-explore-doon.html` remains the only runtime file. No new `<script src>`/`<link>` to external files or build artifacts. New engine JS goes inline inside the existing `<script>` IIFE; new CSS inline inside the existing `<style>` block.
- **HC-2 No UI redesign.** The page is embedded via `<iframe>` into `https://awssbggeu.com/student-community-day`. Preserve existing visual style, the `#AD5CFF` accent and its derived tokens, Plus Jakarta Sans / JetBrains Mono fonts, existing component structure, responsive grid, theme toggle, reduced-motion handling, and `embed=1`/`theme=`/`transparent=1`/`postMessage` resize behavior. Markup/CSS may change only as needed to present richer itinerary output (primary-vs-alternative distinction, per-stop rationale); new components must reuse existing CSS custom properties and class patterns, not introduce a new visual language.
- **HC-3 Never fabricate data.** No invented GPS coordinates, opening hours, prices, or precise road-travel-time numbers not already in or derivable from `D`/`E`. Geographic cluster/route efficiency must be represented via an explicit, clearly-named cluster/area field derived from existing `rt` route-key groupings, `mt`/`far`/`onroute` flags, and ordinary-confidence real-world Dehradun/Mussoorie/Landour geography — not fake coordinates. Any new travel-time-between-clusters numbers must be deterministic, named constants, explicitly commented as estimates, never represented as live traffic data.
- **HC-4 Keep existing passing behavior intact.** `node test/smoke.mjs` currently passes 7 assertions (page load; flight peak-window Return_Deadline fix; three Maggi on-route cases; Summary_Tiles tuned-gating; catalog corrections). These must still pass. Extend the file with new assertions; do not weaken or remove existing ones unless an existing assertion is provably about behavior being intentionally and correctly changed by this upgrade (any such case must be documented explicitly by the step that changes it).
- **HC-5 Keep catalog corrections and image wiring intact.** `ama`→`'AMA Café'`, `hig`→`'The Highland Bakehouse & Pizzeria'` (still `u:1`/unverified placeholder), `mlc`/`ycf` removed, `rdr`/`koi` left as placeholders, and the per-entry `img` fields from the most recent commit must not be reverted or clobbered.
- **HC-6 No new runtime dependencies.** No new database, no new API provider, no road-routing/live-traffic API (none is configured today). Where such an API would help, the design must explain the limitation and implement the best deterministic configurable fallback (named travel-time constants per cluster pair, commented as estimates) — never pretend a static estimate is live traffic.
- **HC-7 Deterministic and explainable.** The engine stays a pure function of its inputs (no hidden randomness), preserving the existing `run()`/`eve()` separation of concerns (pure logic → `show()` DOM write). Any refactor must keep that separation.
- **HC-8 Git.** Commit with clear messages on the current branch (`master`, no worktree, per the prior two feature commits), unless the planning step determines a worktree is genuinely warranted, in which case create it under `.worktrees/` and merge back at the end. No force-push, no amend, no touching git config.

**Known loose end (not in scope of this engine work, mention to the test-writing step as optional bonus only):** `.kiro/specs/scd-explore-doon/tasks.md` has unfinished checklist items 8.4, 8.5, 9, 10 — golden/property tests for the catalog-correction and "Looks open"-pill-removal fixes, plus a final verification pass, left over from the prior UI-pass cycle. These are optional bonus work for the test-writing step, never the primary goal of this engine upgrade.

## Functional Requirements

### FR-A — Stage A: Understand the visitor (structured trip-constraint model)

- FR-A1: The engine SHALL derive a structured representation of the visitor's request from the existing Control_Panel inputs already read at the top of `run()`/`eve()` (`st`, `dm`, `dt`, `tr`, `gr`, `pc`, `sel`) — no new UI controls are introduced; the structure is an internal data shape, not a new input.
- FR-A2: The engine SHALL compute the **actual usable trip duration** (not simply `ret - st`) by explicitly accounting for: outbound travel to the first stop, travel between consecutive stops, time spent at each stop, food/café break time, parking-and-walking overhead where relevant, the return travel leg to campus, and a contingency buffer — extending today's `use = ret - st` plus per-stop `need = tv*2+du_` accounting into a model that is used consistently through filtering, scoring, and assembly rather than only at the single-entry filter stage.
- FR-A3: The engine SHALL NOT produce an itinerary whose simulated finish time (per `sim()`) exceeds the computed `Return_Deadline` (`ret`), consistent with and not weaker than the existing baseline Property 5 ("itinerary finishes within deadline") and Requirement 6.6/6.7 fallback behavior.
- FR-A4: Where the UI already exposes a constraint the baseline engine does not yet use for Stage A reasoning (e.g. `pc` pace, `gr` group type), the engine SHALL fold that constraint into the Stage A trip model rather than only into isolated filter branches as today.

### FR-B — Stage B: Classify and enrich destinations (catalog schema extension)

- FR-B1: The engine SHALL extend — not replace — the existing `D` (Place_Catalog) and `E` (Eatery_Catalog) schemas with an explicit geographic cluster/area field (suggested field name and cluster id set, open to naming refinement at design time, but the *concept* is mandatory): clearly-named cluster ids such as `landour`, `rajpur-rd`, `clement-town`, `city-core`, `fri-nearby`, `other-scenic`, derived from the existing `rt` route-key groupings, the `mt`/`far`/`onroute` flags, and ordinary-confidence real-world Dehradun/Mussoorie/Landour geography.
- FR-B2: The cluster/area field SHALL NOT be backed by fabricated GPS coordinates (per HC-3); it represents a named grouping only, derivable by inspection from data already in the catalog plus common real-world geography knowledge.
- FR-B3: The engine's destination model SHALL retain or add, using the existing schema where possible and extending only where necessary: name/id (`n`/`id`, existing), primary category and secondary tags (`tg`, existing, used as both), experience type (derivable from `tg`/`ty`), recommended visit duration (`du`, existing), typical opening hours (`o`/`c`/`hr`, existing), meal suitability (derivable from `E`'s `ty` and existing `tg` food/cafe tags), scenic/nature/spiritual/adventure/cultural/shopping/café attributes (existing `tg` vocabulary, extended only if a genuinely missing attribute is identified), estimated travel time per relevant pair (new, cluster-pair based — see FR-C3), transportation suitability (existing `mt`/`far`/`ph` flags, extended with explicit per-mode suitability if the design finds the current flags insufficient), and primary-attraction-vs-optional/on-route-stop status (existing `onroute`/`full`/`mt` flags, extended only if needed to distinguish "optional stop" from "on-route-only").
- FR-B4: A destination SHALL be allowed multiple tags (already true via `tg: string[]`), but multiple matching tags SHALL NOT, by themselves, cause the same destination or the same experience type to be recommended repeatedly within one itinerary (see FR-D, the diversity rules) — i.e. tag-count inflation must not leak through scoring into repeated near-duplicate selection, closing root problem #3.
- FR-B5: The engine SHALL NOT fabricate precise coordinates, opening hours, prices, or travel-time estimates for any entry; where a value is an estimate rather than verified fact (e.g. a new cluster-pair travel-time constant), it SHALL be clearly distinguishable in code (naming/comments) as an estimate, consistent with the existing `u:1`/`fx`/`tip`/`hr` conventions already used to mark unverified facts.

### FR-C — Stage C: Build a coherent trip (replacing the "append highest scorers" assembly)

- FR-C1: The engine SHALL evaluate complete candidate itineraries (combinations of stops considered together) rather than independently selecting the single highest-scoring destination for each interest and appending results — this directly replaces the `for(const x of C){...S.push(x);if(S.length>=4)break}` loop described in root problem #1 with an assembly process that considers the itinerary as a whole.
- FR-C2: Itinerary candidate generation and selection SHALL combine: interest matching (existing `it`/`m` vibe-match logic), geographic clustering (new, per FR-B1), route feasibility and travel-time estimation (new per-cluster-pair estimates, per FR-C3, replacing/supplementing the flat `25`-minute city-to-city leg and the fixed `a.tv*.9`/`b.tv*.5+10` heuristics in `leg()`), visit-duration constraints (existing `du`), experience diversity (new, per FR-D), meal timing (new, per FR-F), transportation suitability (existing `mt`/`far`/`ph`/`tr` filters, extended per FR-E), opening-hour constraints (existing `o`/`c`/wait logic), and return-deadline feasibility (existing `ret`/`sim()`/trimming loop, preserved per FR-A3).
- FR-C3: The engine SHALL use deterministic, named, comment-labeled estimated travel-time constants between clusters (per HC-3/HC-6) in place of (or as a refinement of) the current flat `25`-minute and multiplier-based inter-stop legs, so that route feasibility and route efficiency can be judged between any two chosen stops' clusters, not only between campus and a single stop.
- FR-C4: The engine SHALL prioritize candidate itineraries in this exact order (verbatim from the brief, to be implemented as the dominant ordering/penalty structure of the selection logic, not merely as documentation):
  1. Feasibility and returning to campus on time.
  2. Geographic and route efficiency.
  3. Relevance to the visitor's selected interests.
  4. A balanced mix of experiences.
  5. Suitable food and café opportunities.
  6. Appropriate use of available time.
  7. Optional alternatives and flexibility.
- FR-C5: The engine SHALL prefer a geographically sensible itinerary with fewer stops over one with more stops that requires excessive driving — stop count is never itself an optimization target. A 3-stop itinerary confined to one coherent cluster area is an acceptable and often preferable outcome over a 6-stop itinerary spanning distant clusters.
- FR-C6: This requirement does not mandate a specific algorithm (routing library, exhaustive search, etc.) — HC-6 forbids adding a routing library — but does mandate that the *outcome* of FR-C1–C5 be observable: given two itineraries of equal interest-relevance, the one with better geographic/route coherence must be the one the engine selects or renders as primary.

### FR-D — Prevent repetitive recommendations (diversity rules)

- FR-D1: The engine SHALL treat "interests selected" and "number of destinations required to satisfy those interests" as distinct concepts. Selecting N interests (e.g. nature, views, adventure, food) is never, by itself, a signal to include N (or more) separate destinations.
- FR-D2: The engine SHALL avoid recommending two or three destinations that provide essentially the same experience when a more diverse itinerary is achievable within the same time/route constraints.
- FR-D3: The engine SHALL NOT recommend multiple scenic viewpoints merely because more than one candidate matches both "nature" and "views" tags simultaneously (directly closing root problem #3 — today's `D` entries `land`, `geo`, `bha`, `rob` all carry overlapping nature/views/adventure tags and nothing stops more than one being selected together purely because each matches multiple selected vibes).
- FR-D4: The engine SHALL NOT recommend several food stops in one itinerary when a single well-timed meal or café stop is sufficient for the available time and interests.
- FR-D5: The engine SHALL NOT recommend several cafés in one itinerary purely because "cafés"/"food" was among the selected vibes.
- FR-D6: The engine SHALL avoid repeating the same destination across the primary itinerary and the alternatives list (FR-G) unless the repetition is clearly intentional and explained (e.g. presenting the same place as an alternative timing/sequence rather than a duplicate stop).
- FR-D7: Overlapping tags on a single destination SHALL NOT be allowed to inflate that destination's effective priority/score beyond what a single, non-duplicated recommendation of it would warrant — i.e. matching 3 of 4 selected vibes must not make a destination's score equivalent to "worth 3 stops."
- FR-D8: Same-category destinations SHALL be permitted together only when they serve genuinely distinct purposes, are geographically convenient to combine, and fit within the available time — all three conditions, not any one alone.
- FR-D9: The engine SHALL implement an explicit category-diversity score, or an equivalent explicit mechanism, that measurably penalizes or de-weights candidates whose category/experience type duplicates one already selected in the itinerary being assembled.
- FR-D10: These diversity rules are guidance, not a rigid stop-count limit. Longer trips (per FR-H's time-budget behavior) may support more stops when each is genuinely worthwhile and distinct — diversity rules must not become a hardcoded "max N stops" ceiling independent of trip duration.

### FR-E — Transportation and traffic awareness

- FR-E1: Transport mode (`tr`: `car`/`bike`/`none`) SHALL materially affect which destinations are recommended and how the itinerary is timed — not merely gate a small set of hard exclusions and a fixed score nudge as today.
- FR-E2: For two-wheeler (`bike`) mode, the engine SHALL favor destinations that are practical and enjoyable to reach by two-wheeler, SHALL allow longer outings when time permits, and SHALL account for parking, road conditions, and weather exposure considerations in its reasoning/output — without assuming two-wheeler travel eliminates traffic-timing uncertainty.
- FR-E3: For car (`car`) mode, the engine SHALL account for parking and congestion realities and SHALL be more conservative on narrow, busy roads; it SHALL avoid recommending excessive stop counts when congestion is likely, and SHALL use more conservative travel-time estimates when congestion is likely for that cluster/time combination.
- FR-E4: The engine SHALL treat Sunday traffic in Dehradun/Mussoorie/Landour as a key planning constraint via configurable, named traffic-rule constants or traffic-aware estimate adjustments (per HC-6) — not a single flat duration applied uniformly regardless of time-of-day or route.
- FR-E5: The engine SHALL recommend an early start when the itinerary includes Landour/Mussoorie, consistent with and extending the existing `land` entry's `tip` ("leave Landour before about 10 AM...") and the existing `lt.e>630` warning check.
- FR-E6: The engine SHALL account for heavier later-morning traffic on narrow hill roads and possible evening-return congestion in its timing/estimates, and SHALL prefer closer alternatives when a long excursion would leave insufficient return-time buffer.
- FR-E7: WHEN a recommendation depends on an unusually early start, THE engine SHALL clearly indicate that dependency to the visitor in the rendered output (not silently assume it).
- FR-E8: THE engine SHALL use live traffic data only if a live-traffic API is already configured in the project (it is NOT, per HC-6) — otherwise it SHALL use conservative, configurable, named estimate constants and SHALL say so explicitly in-code (and never represent a static estimate as live traffic data in any user-facing or developer-facing text).

### FR-F — Time-budget intelligence (feasibility computed dynamically, not from hardcoded boundaries)

The following time ranges are illustrative examples from the brief, not hardcoded thresholds to branch on literally — the engine SHALL compute feasibility dynamically from the actual usable duration (FR-A2) for any window length, while producing qualitatively the behavior described for windows resembling these examples:

- FR-F1 (~2 hours): Prioritize nearby destinations; avoid any Mussoorie/Landour (`mt`) option that would consume most of the window in transit; consider `city-core`-area destinations; ensure the return time is honored.
- FR-F2 (~4 hours): Produce a coherent local itinerary — nearby cafés, city attractions, or a short scenic outing appropriate to the selected transport mode; avoid distant/impractical destinations; do not assume `car` and `bike` support the same scope of outing in this window.
- FR-F3 (~6 hours): Allow a more substantial outing if route/traffic conditions support it; pick a single sensible geographic cluster rather than spreading across several; include a meal/café stop.
- FR-F4 (~10 hours): Allow a longer Mussoorie/Landour excursion if start time, day, route, and transport mode make it viable; account for traffic and a safe return buffer; do not fill the entire 10 hours with sightseeing (leave room for meals, breaks, and buffer).
- FR-F5: WHEN there is too little time for a distant/high-interest-match attraction the visitor's selections would otherwise suggest, THE engine SHALL explain that clearly and suggest a closer, feasible option, rather than silently dropping the interest or forcing an infeasible itinerary through.

### FR-G — Primary itinerary vs alternatives

- FR-G1: The engine's output SHALL clearly separate the primary sequence the visitor is meant to follow from optional substitute stops ("alternatives").
- FR-G2: The primary itinerary SHALL be chronologically ordered, geographically coherent (per FR-C), feasible (per FR-A3), and SHALL give every stop a clear stated purpose.
- FR-G3: THE engine SHALL offer 1–2 alternatives for suitable stops where available (not for every stop unconditionally, only where a sensible substitute exists).
- FR-G4: Alternatives SHALL NOT count as additional stops in the primary itinerary, and SHALL NOT be included in the primary schedule's total duration/timing computation (`use`/`ret`/`sim()` math).
- FR-G5: Each alternative SHALL explain: what it offers, why a visitor might prefer it over the primary stop it substitutes, whether it fits the route, whether choosing it changes the total duration or return time, and its limitations (e.g. unverified hours, farther from the cluster, etc.).
- FR-G6: Alternatives SHALL be preferred near (geographically/clustered with) the stop they are offered in place of.
- FR-G7: WHERE the existing UI/rendering architecture supports it, selecting an alternative SHALL recalculate the remaining itinerary — leveraging the fact the app already fully re-renders on every `change` event (the existing delegated `document.addEventListener('change', ...)` + debounce + `run()`/`eve()` + `show()` pipeline), rather than introducing a new state-management mechanism.

### FR-H — Geographic and route optimization

- FR-H1: The engine SHALL fix geographically incoherent combinations such as the brief's own example (Landour + Maggi Point + Mindrolling Monastery combined inefficiently in one trip) via clustering (FR-B1) and route-aware sequencing (FR-C).
- FR-H2: THE engine SHALL prefer same-cluster destinations when they offer enough variety to satisfy the visitor's selected interests without forced category duplication (balanced against FR-D).
- FR-H3: THE engine SHALL avoid unnecessary movement between distant clusters/areas.
- FR-H4: THE engine SHALL NOT send the visitor from Landour to a distant area and back toward the city unless clearly justified by interest-fit and time budget.
- FR-H5: THE engine SHALL NOT treat a Rajpur Road café as a "quick stop" if visiting it would cause a substantial detour or break the return schedule.
- FR-H6: WHEN moving from Mussoorie/Landour toward Dehradun, THE engine SHALL consider whether the next candidate stop fits the return route, rather than treating it as an independent choice.
- FR-H7: THE engine SHALL account for outbound and return travel separately (they are not always symmetric in time or route), consistent with existing `tv` (outbound) vs `leg()`/`back()` (return) distinctions, extended per FR-C3.
- FR-H8: THE engine SHALL use actual road-travel estimates where available (i.e. the richer per-cluster-pair constants from FR-C3) rather than arbitrary fixed durations, replacing the current flat `25`-minute city-to-city leg wherever a better cluster-aware estimate is available.
- FR-H9: THE engine SHALL compare complete routes (not single-stop scores) when deciding between competing itinerary candidates, per FR-C1.
- FR-H10: THE engine SHALL penalize backtracking (returning toward/through an already-passed area) in its route evaluation.
- FR-H11: THE engine SHALL reject itineraries that violate the return deadline even when the destinations involved match the visitor's interests perfectly — feasibility (priority 1 in FR-C4) always outranks interest-relevance (priority 3).
- FR-H12: A lightweight scoring/penalty heuristic over cluster adjacency is the appropriate mechanism for all of FR-H1–H11 — no routing library or external mapping API is to be introduced (per HC-6).

### FR-I — Food/café planning

- FR-I1: THE engine SHALL integrate food/café stops into the overall experience narrative rather than treating them as an interchangeable generic add-on, considering: time of day, selected interests, the meal location's position relative to the main attraction(s), total visit duration, and breakfast/lunch/dinner/quick-café suitability.
- FR-I2: THE engine SHALL consider published/known opening hours for meal candidates (existing `o`/`c`/`hr` fields) and whether there is realistically enough time in the itinerary to sit and enjoy the stop, not just pass through it.
- FR-I3: THE engine SHALL NOT assume every visitor wants a full sit-down meal — quick café stops remain a valid, sometimes preferable, outcome depending on time budget and interests.
- FR-I4: THE engine SHALL NEVER invent restaurant/café opening hours. For any entry without confirmed hours, THE engine SHALL reuse the existing Unverified/"Check hours" badge convention (`pill()`'s `x.u` branch) rather than fabricate or infer a specific hours string.

### FR-J — Human-readable, explainable output

- FR-J1: FOR every main stop, THE Output_Panel SHALL display: arrival and departure time, name, travel time from the previous stop, recommended duration at the stop, why it was selected, what to do there, whether it is primary/meal/short-optional, and the next destination plus why that transition makes sense.
- FR-J2: THE engine SHALL extend the existing Directions_Panel/`stp()` guidance pattern to carry this richer per-stop rationale rather than replacing it with a new, parallel presentation mechanism.
- FR-J3: THE Output_Panel SHALL also provide a concise trip overview covering: why the itinerary matches the visitor's selected interests, estimated total travel time, time spent exploring, planned meal/café time, expected return time to campus, a traffic/delay contingency note, and a short explanation of any compromises made (e.g. an interest that could not be fully satisfied within the time budget, per FR-F5).
- FR-J4: All new copy SHALL use natural, non-repetitive, conversational language consistent with the site's existing tone (as seen in existing `note`/`tip`/`fx`/warning strings), not templated boilerplate repeated verbatim per stop.

### FR-K — Timing correctness (exact)

- FR-K1: Both the departure/start time (`st`) and the required return time (`ret`, derived from `dm`/`dt` per the existing Requirement 9/10 formulas) SHALL control the itinerary — neither may be computed or rendered while ignoring the other.
- FR-K2: THE engine SHALL use the actual departure time as the start of the simulated timeline (as `sim()` already does via `let t=st`), and SHALL compute every arrival/departure time from that same running clock.
- FR-K3: THE engine SHALL include inter-stop travel time, time spent at each stop, meal/break time, and the final return-to-campus leg in that running computation — no stage of the pipeline may silently omit one of these components.
- FR-K4: THE engine SHALL include a configurable delay/contingency buffer in the return-time computation (extending, not replacing, the existing fixed buffers already present in the Return_Deadline formulas for `train`/`flight`).
- FR-K5: THE engine SHALL ensure the visitor is back by the required return time (`ret`) for every itinerary presented as the primary plan, consistent with FR-A3/FR-H11.
- FR-K6: THE engine SHALL NEVER display a timetable whose stop/leg durations do not sum consistently to the displayed arrival/departure times (no arithmetic drift between the per-stop rows and the summary figures).
- FR-K7: IF there is insufficient time for any complete itinerary, THEN THE engine SHALL explain that plainly and offer the best feasible itinerary instead (extending, not replacing, the existing `fail()`/best-single-stop-options fallback behavior in `run()`/`eve()`).
- FR-K8: THE engine SHALL continue to use exactly one time representation throughout — minutes-of-day integers via the existing `tm()`/`fm()` helpers — introducing no second time representation.
- FR-K9: Midnight-crossing SHALL remain explicitly out of scope. Evening mode continues to end by about 11 PM (existing `eve()` behavior). THE engine SHALL validate inputs to prevent nonsensical overnight ranges rather than add overnight-itinerary support, unless a given fix is genuinely trivial — any case where this is judged non-trivial SHALL be noted explicitly as out of scope rather than silently worked around.

### FR-L — Explain recommendations and flexibility

- FR-L1: THE engine SHALL communicate why each destination in the primary itinerary was selected (per FR-J1) and, where feasible within the existing architecture, why plausible alternatives were excluded or demoted to the alternatives list (per FR-G).
- FR-L2: WHERE the existing UI/architecture supports it, THE engine SHALL allow: replacing a stop with an alternative (per FR-G7), skipping an optional stop, exploring another itinerary variant, adjusting pace (existing `pc` control), and recalculating after any such change.
- FR-L3: AFTER any such change, THE engine SHALL recompute travel times, remaining time budget, and the return journey — a stop replacement or skip SHALL NEVER silently leave the displayed schedule internally inconsistent (ties directly to FR-K6).
- FR-L4: Only interactions that integrate cleanly into the current single-file, render-on-every-change-event architecture (the existing delegated `change` listener + 40ms debounce + `run()`/`eve()` + `show()` pipeline) SHALL be implemented. No new interaction model (e.g. a separate client-side router, a new global reactive store) is in scope.

## Non-Functional Requirements

- NFR-1 (Determinism/testability): The engine SHALL remain a pure function of its inputs with no hidden randomness, Date-based nondeterminism, or network dependency, preserving the existing `run()`/`eve()` → `show()` separation so logic remains unit-testable independent of the DOM (per HC-7).
- NFR-2 (No new dependencies): No new npm package, build tool, external API, or database may be introduced (per HC-6); `jsdom` remains the only dev dependency and `test/smoke.mjs` remains the only test entry point unless the test-writing step adds a sibling file under `test/`.
- NFR-3 (Backward compatibility): All 7 existing `node test/smoke.mjs` assertions SHALL continue to pass unmodified in intent (per HC-4); the engine upgrade is additive/corrective to Stage A/B/C reasoning, not a rewrite that discards the existing baseline filter/scoring/trim pipeline wholesale.
- NFR-4 (Single-file footprint): The upgrade SHALL NOT materially change the "single self-contained HTML file" distribution model; any new data (cluster ids, travel-time constants) lives inline in the existing `<script>` block (per HC-1).
- NFR-5 (Explainability over cleverness): Where a design choice trades off algorithmic sophistication against explainability (e.g. an exhaustive-but-opaque combinatorial search vs. a simpler, inspectable penalty/heuristic model), the simpler, explainable, and non-fabricating option is required (per HC-6's "no routing library" and FR-H12's "lightweight scoring/penalty heuristic").
- NFR-6 (Visual/brand non-regression): No change may alter the `#AD5CFF` accent, derived tokens, font stacks, or embed/theme/transparent query-param behavior (per HC-2).

## Acceptance Criteria

1. AC-1: WHEN the same inputs (`st`, `dm`, `dt`, `tr`, `gr`, `pc`, `sel`) are supplied to `run()`/`eve()` twice, THE engine SHALL produce byte-identical output both times (determinism, NFR-1).
2. AC-2: WHEN an itinerary includes two or more candidate stops that score similarly on interest-match but differ in geographic cluster, THE engine SHALL select the combination with better route coherence over the combination with worse route coherence, all else equal (FR-C4 priority 2 before priority 3).
3. AC-3: WHEN a visitor selects nature + views + adventure (three vibes matched by multiple overlapping-tag `D` entries such as `land`, `geo`, `bha`, `rob`), THE engine SHALL NOT include more than one of those near-duplicate nature/views/adventure experiences in the primary itinerary unless the time budget and geography genuinely support more than one distinct experience (FR-D2/D3/D8/D9).
4. AC-4: WHEN a visitor selects "food" or "cafés" as a vibe with no other strong meal-driving signal, THE engine SHALL include at most one meal/café stop in the primary itinerary, not one per matching candidate (FR-D4/D5).
5. AC-5: WHEN the usable time window is small enough that a Mountain_Trip (`mt`) destination would consume most of it in transit (~2-hour-scale example, FR-F1), THE engine SHALL exclude Mountain_Trip options from the primary itinerary and SHALL favor `city-core`/nearby clusters instead, while still returning the visitor by `ret`.
6. AC-6: WHEN the usable time window is large (~10-hour-scale example, FR-F4) AND the start time/day/route/transport mode make a Mussoorie/Landour excursion viable, THE engine SHALL allow such an excursion but SHALL NOT fill the entire window with sightseeing — meal/break/buffer time SHALL be visibly present in the output.
7. AC-7: WHEN a selected interest cannot be feasibly satisfied within the time budget (e.g. a far cluster with a short window), THE engine SHALL render an explanation of the shortfall and offer the closest feasible alternative, rather than omitting the interest silently or forcing an infeasible plan through (FR-F5, directly testable via rendered `.wn`-style notice text).
8. AC-8: WHEN transport mode changes from `car` to `bike` with all other inputs held constant, THE rendered itinerary and/or its travel-time estimates/notes SHALL differ in at least one materially observable way (destination set, timing, or guidance text) for at least one representative input combination (FR-E1), closing root problem #5.
9. AC-9: WHEN the plan includes a Mussoorie/Landour-area stop, THE rendered output SHALL include an early-start recommendation and/or a Sunday-traffic-aware note, consistent with and extending the existing `land` entry's `tip` text and the `lt.e>630` check (FR-E4/E5).
10. AC-10: WHEN a meal/café stop is included, THE engine SHALL render why it was placed where it was (time-of-day fit, proximity to the preceding/following stop) rather than only a generic "lunch" label (FR-I1/FR-J1).
11. AC-11: THE engine SHALL NEVER render a fabricated opening-hours string, price, or address for any entry flagged `u:1`; only the existing "Check hours"/"Unverified" placeholder convention (`pill()`) and the entry's existing placeholder `hr` text SHALL ever render for such entries (FR-I4/HC-3, extending baseline Property 9).
12. AC-12: FOR every main stop in the rendered primary itinerary, THE output SHALL contain: arrival+departure time, name, travel time from the previous stop, recommended duration, a stated reason for selection, a stated activity, a primary/meal/short-optional designation, and (for all but the last stop) a stated reason the next destination follows logically (FR-J1).
13. AC-13: WHERE at least one alternative is offered for a primary stop, THE alternative's rendered block SHALL be visually/structurally distinguishable from a primary stop, SHALL state what it offers, why one might prefer it, route fit, duration/return-time impact, and limitations, and SHALL NOT be counted in the primary schedule's total duration (FR-G1–G5).
14. AC-14: THE sum of each primary stop's displayed duration plus every displayed inter-stop/return travel leg SHALL exactly equal the difference between the displayed start time and the displayed final return-to-campus arrival time, for every rendered itinerary (FR-K6, no arithmetic drift).
15. AC-15: THE engine SHALL continue to reject (trim down or fall back on) any itinerary whose simulated finish time exceeds `ret` (or `min(ret, Daylight_Cutoff)` when a Mountain_Trip stop is present), even when a rejected combination would have scored highest on interest-match (FR-H11, extending baseline Property 5).
16. AC-16: `node test/smoke.mjs`'s existing 7 assertions (`smoke`, `golden (8.1)`, `golden (8.2a/b/c)`, `golden (8.3)`, `golden (8.4)`) SHALL still pass after the engine upgrade (HC-4/NFR-3).
17. AC-17: No new `<script src>`, `<link>` to an external file, new npm dependency beyond `jsdom`, new database, or new external API call SHALL be introduced anywhere in the diff (HC-1/HC-6/NFR-2/NFR-4).
18. AC-18: THE `#AD5CFF` accent token, the Plus Jakarta Sans/JetBrains Mono font-family declarations, the `embed=1`/`theme=`/`transparent=1` query-param handling, and the `postMessage`-based iframe resize behavior SHALL be present and functioning unchanged after the upgrade (HC-2/NFR-6).

## Required Test Scenarios (A–L)

These are the scenario-level checks downstream design/plan/code steps must trace to, in addition to the numbered acceptance criteria above. Each is independently checkable against rendered `#out` HTML via the existing `test/smoke.mjs` harness pattern (`loadPage`/`setValue`/`selectRadio`/`toggleCheckbox`/`getOutHTML`).

- **Scenario A — Short window (~2h), day mode.** Narrow `st`/`dt` gap. Expect: no Mountain_Trip stop; nearby/`city-core` stops only; `ret` honored. Traces to FR-F1, AC-5.
- **Scenario B — Medium window (~4h), day mode, both `tr=car` and `tr=bike`.** Expect: a coherent local itinerary that differs materially between the two transport modes (destination set, timing, or guidance); no distant/impractical stop in either case. Traces to FR-F2, FR-E1, AC-8.
- **Scenario C — Extended window (~6h), day mode.** Expect: a single sensible cluster chosen (not stops scattered across clusters), with a meal/café stop present. Traces to FR-F3, FR-C5.
- **Scenario D — Full-day window (~10h), day mode, early start.** Expect: a Mussoorie/Landour excursion is allowed, with visible buffer/meal time (not fully packed with sightseeing) and a safe return margin. Traces to FR-F4, AC-6.
- **Scenario E — Interest infeasible within window.** A far-cluster interest selected with a window too short to reach it. Expect: an explicit explanation plus a closer feasible alternative is rendered; the interest is not silently dropped nor force-included past the deadline. Traces to FR-F5, AC-7, AC-15.
- **Scenario F — Multi-interest diversity (nature + views + adventure + food selected together).** Expect: no 2–3 near-duplicate scenic/adventure stops selected together purely from overlapping tags; at most one meal/café stop. Traces to FR-D2–D9, AC-3, AC-4.
- **Scenario G — Geographic coherence / anti-backtracking.** Construct an input where the baseline-style assembly would combine stops from distant clusters (the brief's own Landour + Maggi + Mindrolling example). Expect: the engine either avoids the incoherent combination or clearly flags/penalizes it in favor of a same-cluster alternative. Traces to FR-H1–H11, AC-2.
- **Scenario H — Transport-mode materiality under traffic-likely conditions.** Compare `car` vs `bike` on a Sunday/hill-road itinerary. Expect: observable differences in destination suitability notes, stop-count conservatism, and/or travel-time estimates. Traces to FR-E1–E3, AC-8.
- **Scenario I — Sunday/traffic-aware timing for a Landour/Mussoorie plan.** Expect: early-start recommendation present, later-morning/evening congestion considerations reflected in timing or copy, and an explicit statement that estimates are configurable/deterministic, not live traffic. Traces to FR-E4–E8, AC-9.
- **Scenario J — Meal/café planning across time-of-day.** Compare a morning-start plan vs. an afternoon-start plan with "food" selected. Expect: different meal-stop placement/type (breakfast-adjacent vs. lunch-adjacent vs. quick café) rather than an identical generic insertion; no fabricated hours for `u:1` eateries. Traces to FR-I1–I4, AC-10, AC-11.
- **Scenario K — Primary vs alternatives rendering and recompute.** A plan where at least one stop has a plausible same-cluster substitute. Expect: alternative(s) rendered distinctly, not counted toward total duration, with the required explanatory fields (FR-G5); where the UI supports selection, choosing the alternative recomputes the remaining schedule consistently (FR-L3). Traces to FR-G1–G7, FR-L1–L4, AC-13, AC-14.
- **Scenario L — Regression and constraint compliance.** Run the full existing `test/smoke.mjs` suite; grep the diff for new `<script src>`/`<link>` tags, new `package.json` dependencies, new fabricated coordinate/hour/price literals, and confirm the `#AD5CFF`/font/embed-param behavior is untouched. Traces to HC-1–HC-7, NFR-1–NFR-6, AC-16–AC-18.

## Out of Scope

- Adding a real routing/mapping API, live traffic data source, or any new network dependency (HC-6). The engine must achieve route-awareness entirely through the deterministic cluster/estimate model in FR-B/FR-C/FR-H.
- Fabricating GPS coordinates, opening hours, prices, or any other unverified fact for any catalog entry, including the still-open baseline placeholders (`rdr`, `koi`, Highland's full real data) — these remain explicit "Check hours"/Unverified placeholders per HC-5 and FR-I4.
- Overnight/midnight-crossing itinerary support (FR-K9) — evening mode continues to end by about 11 PM; this upgrade only needs to validate inputs sensibly, not add cross-midnight scheduling, unless trivial.
- Any UI/visual redesign beyond what is strictly necessary to render primary-vs-alternative distinction and per-stop rationale within the existing token set (HC-2).
- A new interaction/state-management architecture; all new interactivity must fit the existing delegated-`change`-listener + debounce + full-rerender model (FR-L4).
- Completing the unrelated, already-tracked baseline test-suite gaps (`tasks.md` items 8.4, 8.5, 9, 10) as a primary deliverable of this engine upgrade — they may be picked up as optional bonus work by the test-writing step only.
- Introducing a new build step, bundler, or splitting `scd-explore-doon.html` into multiple files (HC-1/NFR-4).

## Assumptions (flagged for design-review scrutiny)

- A1: The brief's cluster id examples (`landour`, `rajpur-rd`, `clement-town`, `city-core`, `fri-nearby`, `other-scenic`) are illustrative, not an exhaustive or final list — the design step should derive the actual cluster set and field name from a full pass over every `D`/`E` entry's existing `rt`/`mt`/`far`/`onroute` data and known geography, and may add or rename clusters as needed as long as HC-3 (no fabricated coordinates) holds.
- A2: "Evaluate complete itinerary combinations" (FR-C1) does not require literal brute-force enumeration of all subsets of `D`/`E` — a bounded/greedy-with-lookahead or cluster-first-then-fill approach that still satisfies FR-C4's priority ordering and AC-2/AC-15 is acceptable, since HC-6 forbids adding a routing/optimization library and NFR-5 prefers explainable heuristics over opaque combinatorial search.
- A3: FR-B3's "transportation suitability... extended with explicit per-mode suitability if the design finds the current flags insufficient" is a conditional extension, not a mandatory new field — if the existing `mt`/`far`/`ph`/`tr`-filter combination already lets FR-E's requirements be met, no new field is required.
- A4: Where this document says "the engine SHALL" for behavior that is naturally a `run()`-only (day mode) concern (e.g. Mountain_Trip/Landour-specific items in FR-E4–E6, FR-F, FR-H), the corresponding `eve()` (evening mode) path is not required to implement the same mountain/hill-road logic, since evening-mode itineraries are city-area by construction today — this mirrors how baseline Requirement 11 (Daylight Constraint) is already `run()`-scoped only.
